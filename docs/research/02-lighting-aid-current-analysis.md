# lighting-aid 현재 앱 분석 (v3.0, commit 37a27ec 기준)

> 소스 전체(약 3,000줄)를 읽고, 로컬 dev 서버로 실제 화면을 띄워 확인한 결과를 정리한다.
> 스크린샷: `img/current-landing.jpg`, `img/current-editor.jpg`

---

## 1. 한 줄 요약

**2D 평면도(top-down) 위에서 무대 조명기의 위치·타겟·렌즈를 조작하면, 3D 원뿔 투사를 계산해 바닥(z=0)과 배우 얼굴 높이에 생기는 빛의 타원을 그려 주는 정적 웹앱**이다. 씬(큐)별로 조명 구성을 따로 저장할 수 있으며, 밝기 Probe와 채널 사용 현황(패치) 패널을 함께 제공한다.

---

## 2. 기술 스택과 배포

| 항목 | 내용 |
|---|---|
| 빌드 | Vite 8 |
| 언어 | Vanilla TypeScript 6 (`verbatimModuleSyntax: true` → 타입은 `import type` 필수) |
| 렌더링 | HTML5 Canvas 2D |
| UI | 프레임워크 없음. 템플릿 문자열로 `innerHTML`을 만들고, 이벤트는 `onclick="..."` + `window` 전역 함수로 연결 |
| 상태 | 전역 `AppState` 1개 + 직접 만든 Pub/Sub(`subscribe`/`notify`) |
| 저장 | JSON 파일 다운로드/업로드 (서버·DB 없음) |
| 배포 | GitHub Actions → GitHub Pages (`main` 푸시 시 자동). `vite.config.ts`에서 Actions 환경일 때 `base`를 `/<repo>/`로 설정 |
| 의존성 | devDependencies에 `typescript`, `vite`만 존재. 런타임 의존성 0개 |

## 4. 화면 구성

### 4-1. 랜딩 화면
- 극장 평면도를 흐리게 깐 배경 위에 카드 하나가 떠 있다.
- "작업 공간 선택": **Sandbox**(빈 10m×10m) / **Humanities**(12m×22.7m 극장 도면) 카드 2개 + "파일 불러오기".

### 4-2. 에디터 (3단 고정 레이아웃)

```
┌──────────┬───────────────────────────────────────┬──────────────┐
│ 씬 [+추가]│ 앱이름 | 폭 깊이 배우높이 기본Z | + - 초기화 | 불러오기 저장 │
│ ┌──────┐ ├───────────────────────────────────────┤ 조명 기구     │
│ │썸네일 │ │                                       │ [Fixed▾][+추가]│
│ │Scene1│ │          캔버스 (평면도 + 빛 타원)        │ L1 (Center)  │
│ └──────┘ │                                       │ ...목록...    │
│          │                                       ├──────────────┤
│          │                                       │ ▸ 위치 XYZ    │
│ ▸배경 이미지│                                     │ ▸ 채널/타입/광학│
│ ▸전체 보기 │                                     │ □ 셔터 컷     │
│   옵션    │                                       │ 밝기 Probe    │
│          │                                       │ 채널 사용 현황 │
└──────────┴───────────────────────────────────────┴──────────────┘
  280px                   flex                          360px
```

| 영역 | 내용 |
|---|---|
| 좌측(280px) | 씬 목록(썸네일 + 이름 변경/복사/삭제, 드래그 순서 변경), 씬별 배경 이미지 설정, 전체 보기 옵션(바닥/얼굴 높이/빔/필드/극장 평면도/캣워크 토글) |
| 상단 헤더 | 앱 이름, 무대 폭·깊이·배우 높이·기본 Z 숫자 입력, 줌 +/−/초기화, 파일 불러오기, 저장 |
| 중앙 | 캔버스. 어두운 배경 위에 평면도, 빛 타원(바닥=흰/노랑, 얼굴=빨강 점선), 조명 마커(파란 사각형), 타겟(노란 원), 셔터 핸들(빨간 점), Probe(녹색 십자) |
| 우측(360px) | 조명 추가(타입 선택), 조명 목록, 속성 패널(접이식: 위치/채널·타입·광학/셔터), 밝기 Probe, 채널 사용 현황 |

## 5. 기능 목록

### 5-1. 광학 엔진 (`engine/geometry.ts`)
- 조명기 4종과 각 제원
  - **Fixed Ellipsoidal**(19°/26°/36°/51° 렌즈)
  - **Zoom Ellipsoidal**(Narrow 15–30°, Medium 25–50°)
  - **Fresnel**(narrow ↔ medium ↔ flood 연속 포커스)
  - **PAR**(VNSP/NSP/MFL/WFL, 램프 회전각)
- 위치(x, y, z)와 타겟(x, y)으로 Tilt/Pan 각을 계산한다.
- 원뿔과 수평면(z=0, z=배우 높이)의 교차 타원을 계산하고, Beam/Field를 구분한다.
- 셔터(4점 다각형)를 바닥 좌표에서 얼굴 높이로 역투영해 클리핑한다(Ellipsoidal 계열만).
- **Probe 밝기**: 한 지점에서 조명별 기여도(거리, 각도, 프로파일, 셔터 차단 여부)를 상대값(rel)으로 합산한다.

### 5-2. 캔버스 상호작용 (`render/canvas.ts`)
| 동작 | 결과 |
|---|---|
| 선택된 조명 마커 드래그 | 조명 위치 이동 |
| 타겟(노란 원) 드래그 | 조준점 이동 |
| 셔터 꼭짓점 드래그 | 셔터 형태 변경 |
| Probe 드래그 | 측정 지점 이동 |
| 다른 조명 클릭 / Ctrl+클릭 | 단일 선택 / 다중 선택 토글 |
| 빈 공간 드래그 | 화면 이동(팬) |
| 마우스 휠 | 커서 기준 확대/축소 |
| Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z | 실행 취소 / 다시 실행 |

### 5-3. 씬(큐) 관리 (`ui/scene.ts`)
- 추가, 복사, 이름 변경, 삭제, 드래그로 순서 변경.
- 씬마다 160×160 썸네일을 상태가 바뀔 때마다 자동으로 다시 생성한다.
- 씬마다 배경 이미지(세트 도면)를 Base64로 넣고 위치·크기·투명도를 조절한다.

### 5-4. 조명 관리 (`ui/fixture.ts`)
- 타입을 골라 추가, 선택, 숨기기, 삭제.
- 속성: 위치 XYZ, 채널 번호, 타입 변경, 타입별 광학 설정, 셔터 사용 여부.

### 5-5. 극장 프리셋 (`config/venues.ts`)
- Sandbox, Humanities(인문소극장) 2종.
- Humanities는 평면도와 캣워크 오버레이 레이어, 기본 조명 높이 5.74m를 제공한다.

### 5-6. 채널 사용 현황 (`ui/patch.ts`, `config/patch.ts`)
- Humanities 극장의 디머 채널 91개를 캣워크 위치별 행으로 보여 준다.
- 전체 씬을 훑어 채널별 참조 수를 세고, 콘센트 수를 넘으면 `over` 상태로 경고한다.

### 5-7. 저장
- `prompt()`로 파일명을 받아 `AppState` 전체를 JSON으로 다운로드한다.
- 불러오기 시 `normalizeFixtureSelection()`이 구버전 데이터를 보정한다(타입 기본값, 셔터 다각형 등).

## 6. 아키텍처 특징과 현재의 한계

### 잘 되어 있는 점
- **엔진과 UI가 분리**되어 있다. `GeometryEngine`은 DOM을 모르는 순수 계산 클래스이므로, UI를 갈아엎어도 그대로 재사용할 수 있다.
- **단일 상태 + Undo/Redo** 구조가 단순하고 예측 가능하다.
- 타입 정의가 촘촘하다(조명 4종 판별 유니언, 셔터 4점 튜플).
- 런타임 의존성이 없어서 배포가 가볍다.

### SketchUp식으로 옮길 때 걸림돌이 되는 점
| 한계 | 영향 |
|---|---|
| 모든 상태 변경마다 **전체 UI를 `innerHTML`로 다시 그림** | 플로팅 패널, 입력 포커스 유지, 애니메이션 같은 정교한 UI를 만들기 어렵다. |
| 이벤트를 `window` 전역 함수 + 인라인 `onclick`으로 연결 | 컴포넌트 단위로 쪼개기 어렵고, 같은 UI를 두 곳에 두기 어렵다. |
| `setState` 때마다 **썸네일을 동기적으로 재생성** | 드래그 중 매 프레임 오프스크린 렌더 비용이 든다. 씬이나 조명이 늘면 느려진다. |
| 레이아웃이 **고정 3단** | 캔버스 영역이 좁다(1440px 화면에서 약 800px). 캔버스 우선 레이아웃으로 바꾸려면 구조 변경이 필요하다. |
| "도구(tool)" 개념이 없음 | 지금은 무엇을 클릭했는지에 따라 동작이 암묵적으로 결정된다. 선택/이동/조준/셔터/Probe/팬 같은 **명시적 도구 모드**가 없다. |
| 극장 채널 표가 Humanities에 하드코딩 | 다른 극장을 추가하려면 데이터 모델 일반화가 필요하다. |
| 저장이 상태 전체 덤프 | `interaction`, `thumbnail` 같은 런타임 값까지 파일에 들어간다. 서버 저장을 하려면 **문서 모델(Project/Document)과 UI 상태를 분리**해야 한다. |
| 프로젝트 개념 없음 | 파일 = 상태 1개. 파일 목록, 최근 작업, 썸네일 카드 같은 홈 화면을 만들려면 프로젝트 메타데이터(이름, 극장, 수정일, 썸네일)가 필요하다. |
| `index.html` 인라인 스타일과 `style.css`가 혼재 | 디자인 토큰을 한곳에서 관리하기 어렵다. |

## 7. 결론

- **재사용할 자산**: `GeometryEngine`, 타입 정의, 극장/채널 데이터, 캔버스 그리기 함수(`drawCueToContext`).
- **재설계가 필요한 부분**: 레이아웃 셸(캔버스 우선 + 플로팅 패널), 도구 시스템, UI 렌더링 방식(컴포넌트화), 문서 모델과 저장 계층(로컬 → 클라우드 대비), 홈/프로젝트 화면.
- 구체적인 적용안은 `03-lighting-aid-sketchup-mapping.md`에 정리한다.
